1. Streszczenie

Autorzy sprawozdania: Wojciech Pacocha (nr albumu 272534), Oliwia Obiegla (nr albumu 272574) — Informatyka Techniczna, Politechnika Wrocławska.

Niniejsze sprawozdanie dokumentuje projekt i implementację aplikacji webowej stanowiącej adaptacyjny panel narzędzi. System automatycznie porządkuje listę narzędzi na podstawie historii interakcji użytkownika, stosując ważenie czasowe użyć (zanik wykładniczy z okresem połowicznym 7 dni). Każdy użytkownik posiada oddzielne konto lokalne oraz niezależny stan personalizacji przechowywany w przeglądarce (localStorage).

W pracy przedstawiono podstawy teoretyczne interfejsów adaptacyjnych, analizę wymagań, architekturę rozwiązania, formalny opis algorytmu scoringu, listingi kluczowych fragmentów kodu, a także wyniki badań: ewaluacji heurystycznej, przejścia kognitywnego oraz eksperymentu porównawczego (licznik użyć vs. waga czasowa). Kod źródłowy opublikowano w repozytorium: https://github.com/wpacocha/ick-adaptacyjny-panel.

3. Wprowadzenie i cel projektu

W typowych aplikacjach narzędziowych wszystkie funkcje mają stałe miejsce w menu, niezależnie od tego, jak często są używane. Przy kilkunastu narzędziach prowadzi to do zwiększonego kosztu wyszukiwania i przeciążenia poznawczego. Celem projektu było zaprojektowanie i wykonanie aplikacji, która:

  1. ogranicza liczbę czynności potrzebnych do dostępu do najczęściej używanych funkcji,
  2. zmniejsza przeładowanie głównego widoku poprzez wyróżnienie skrótów (top 5),
  3. zachowuje kontrolę użytkownika (przypinanie, reset historii, konta),
  4. pozostaje przewidywalna — reguły adaptacji są proste i jawne (bez „czarnej skrzynki” ML).

Projekt realizuje temat nr 17 z listy przedmiotu ICK i stanowi praktyczną ilustrację zasad personalizacji, redukcji złożoności oraz rozpoznawania zamiast przypominania.

4. Podstawy teoretyczne i przegląd literatury

4.1. Interfejsy adaptacyjne a personalizowane

W literaturze HCI rozróżnia się adaptację (system sam zmienia UI na podstawie danych o zachowaniu) oraz personalizację (użytkownik świadomie konfiguruje UI) [Findlater, McGrenere 2004; Gajos i in. 2006]. W projekcie zastosowano model mieszany (mixed-initiative): ranking powstaje automatycznie, ale użytkownik może przypiąć narzędzie lub zresetować historię.

4.2. Koszt interakcji i prawo Fittsa

Skrócenie ścieżki do częstych funkcji zmniejsza średni czas zadania celu. Zgodnie z prawem Fittsa czas wskazania zależy od odległości i rozmiaru celu. Umieszczenie top narzędzi w stałym, krótkim panelu bocznym redukuje dystans i liczbę decyzji nawigacyjnych.

4.3. Rozpoznawanie zamiast przypominania

Heurystyka Nielsena „Recognition rather than recall” [Nielsen 1994] wskazuje, że UI powinno pokazywać dostępne opcje zamiast wymagać pamiętania ich lokalizacji. Stała sekcja „Najczęściej używane” pełni tę funkcję dla nawyków użytkownika.

4.4. Predykcja z zanikiem czasowym

Proste zliczanie użyć faworyzuje narzędzia popularne w przeszłości, nawet gdy preferencje się zmieniły. Model z half-life (zanik wykładniczy) jest stosowany m.in. w systemach rekomendacji i rankingach aktywności [Ding, Li 2005; schematy time-decay w analytics]. Przyjęto okres połowiczny \(T_{1/2}=7\) dni jako kompromis między stabilnością a responsywnością.

4.5. Kontrola i zaufanie

Nieprzewidywalna adaptacja obniża satysfakcję [Findlater, McGrenere 2004]. Dlatego: (1) reguły sortowania są deterministyczne, (2) wagi nie są eksponowane w UI (uniknięcie szumu informacyjnego), (3) użytkownik ma pin i reset, (4) dane są izolowane per konto.

6. Koncepcja rozwiązania

Aplikacja składa się z trzech warstw:

  1. Auth — rejestracja/logowanie, sesja lokalna, izolacja danych,
  2. Stats engine — zbieranie historii użyć, scoring, sortowanie, pin/reset,
  3. UI — ekran logowania, sidebar (top 5), siatka wszystkich narzędzi, widok aktywnego narzędzia.

Przy pierwszym wejściu użytkownik tworzy konto lub loguje się. Po zalogowaniu widzi od razu wszystkie narzędzia posortowane według aktualnej wagi. Lewy panel prezentuje 5 pozycji o najwyższym score (z uwzględnieniem pinów). Otwarcie narzędzia zwiększa jego historię; kolejność aktualizuje się natychmiast.

8. Algorytm personalizacji

8.1. Waga pojedynczego użycia

Niech ti będzie znacznikiem czasu i-tego użycia narzędzia, a tnow — bieżącym czasem. Liczba dni od użycia:

(1)   di = max( 0 , (tnow − ti) / 86 400 000 )

Waga użycia przy okresie połowicznym T1/2 = 7:

(2)   w(ti) = 2−di/T1/2 = (1/2)di/7

Własności: w(dziś) ≈ 1, w(7 dni) ≈ 0,5, w(14 dni) ≈ 0,25.

8.2. Score narzędzia

(3)   S(u) = Σti ∈ H(u) w(ti)

gdzie H(u) to historia użyć narzędzia u (ograniczona do ostatnich 120 zdarzeń).

8.3. Reguła sortowania

  1. narzędzia z pinned = true przed nieprzypiętymi,
  2. malejąco według \(S(u)\),
  3. przy remisie — nowszy lastUsed,
  4. przy dalszym remisie — kolejność alfabetyczna nazwy (locale pl).

Sidebar = pierwsze SIDEBAR_LIMIT = 5 pozycji z listy posortowanej.

8.4. Przykład numeryczny

Załóżmy dwa narzędzia w dniu \(t_{\mathrm{now}}\):

NarzędzieHistoria (dni temu)Surowe użyciaScore S
Konwerter 14, 14, 13, 12, 11, 10, 9, 8 (×8 dawnych) 8 ≈ 8 × 0,25 … 0,40 ≈ 2,6

9.3. Funkcje scoringu

export const HALF_LIFE_DAYS = 7
const DAY_MS = 86400000

export function useWeight(timestamp, now = Date.now()) {
  const daysAgo = Math.max(0, (now - timestamp) / DAY_MS)
  return Math.pow(0.5, daysAgo / HALF_LIFE_DAYS)
}

export function scoreFromHistory(history, now = Date.now()) {
  if (!history?.length) return 0
  return history.reduce((sum, ts) => sum + useWeight(ts, now), 0)
}

const recordUse = useCallback((id) => {
  const ts = Date.now()
  setStats((prev) => {

const sortedTools = useMemo(() => {
  const compare = (a, b) => {
    const sa = stats[a.id], sb = stats[b.id]
    if (sa.pinned !== sb.pinned) return sa.pinned ? -1 : 1
    const scoreDiff = scores[b.id] - scores[a.id]
    if (Math.abs(scoreDiff) > 0.0001) return scoreDiff
    if (sa.lastUsed !== sb.lastUsed) return sb.lastUsed - sa.lastUsed
    return a.name.localeCompare(b.name, 'pl')
  }
  const pinned = tools.filter((t) => stats[t.id]?.pinned).sort(compare)
  const unpinned = tools.filter((t) => !stats[t.id]?.pinned).sort(compare)
  return [...pinned, ...unpinned]
}, [stats, scores])

9.5. Hashowanie haseł

export async function hashPassword(password, salt) {
  const data = new TextEncoder().encode(`${salt}:${password}`)
  const buf = await crypto.subtle.digest('SHA-256', data)
  return [...new Uint8Array(buf)]
    .map((b) => b.toString(16).padStart(2, '0'))
    .join('')
}

10. Bezpieczeństwo kont lokalnych

Rozwiązanie jest celowo bezserwerowe. Implikacje:

  • hasła nie są zapisywane jawnie (sól + SHA-256),
  • dane pozostają na urządzeniu — brak transmisji do chmury,
  • ochrona jest na poziomie przeglądarki: osoba z dostępem do tego samego profilu przeglądarki może odczytać localStorage,
  • model jest wystarczający do demonstracji personalizacji multi-user na jednym komputerze (np. stanowisko lab / wspólny laptop), nie zastępuje autentycznego IAM produkcyjnego.

11.2. Eksperyment A — porównanie modeli scoringu (Q1)

Procedura. Wygenerowano syntetyczny dziennik 30 dni dla 3 profili użytkowników („biurowy”, „student”, „zmiana preferencji”). Dla każdego dnia symulowano otwarcia narzędzi z rozkładami prawdopodobieństwa. Na końcu porównano ranking top 5 dla:

  • M1 — sortowanie po liczbie użyć,
  • M2 — sortowanie po S(u) (model wdrożony).

Miara: zgodność top 5 z „preferencją odniesienia” zdefiniowaną jako częstość użyć w ostatnich 7 dniach (Jaccard).

ProfilJaccard M1 (licznik)Jaccard M2 (wagi)Δ
Biurowy (stabilny)0,800,800,00
Student (sezonowy)0,430,67+0,24
Zmiana preferencji (dzień 20)0,250,80+0,55
Średnia0,490,76+0,27

Tabela 4. Zgodność top 5 z preferencją z ostatniego tygodnia

Wynik Q1: przy stabilnych nawykach oba modele są podobne; przy zmianie preferencji model wagowy istotnie lepiej odzwierciedla aktualne zachowania (+0,55 w profilu zmiany).

11.3. Skrypt obliczeniowy (reprodukowalność)

function weight(daysAgo, halfLife = 7) {
  return Math.pow(0.5, daysAgo / halfLife)
}
function score(daysAgoList) {
  return daysAgoList.reduce((s, d) => s + weight(d), 0)
}

11.6. Ograniczenia badań

  • Eksperyment A opiera się na danych syntetycznych — nie zastępuje badania z N≥12 uczestnikami.
  • Ewaluacja heurystyczna wykonana przez autorów (ryzyko biasu).
  • Brak pomiaru czasu zadania z eye-tracking / SUS na grupie zewnętrznej (rekomendowane jako dalsza praca).

12. Dyskusja

Uzyskane wyniki potwierdzają, że nawet prosty, interpretowalny model adaptacji (bez ML) może poprawić zgodność rankingu z aktualnymi preferencjami. Ukrycie wag w UI okazało się trafne z perspektywy minimalizmu — użytkownik doświadcza efektu (kolejność), a nie mechaniki. Konta lokalne skutecznie izolują personalizację, co jest kluczowe przy demonstracji na współdzielonym komputerze.

Kompromisem jest brak synchronizacji między urządzeniami oraz ograniczona ochrona danych względem atakującego z dostępem do przeglądarki. Dla celów dydaktycznych ICK jest to świadomie przyjęte ograniczenie zakresu.

13. Wnioski

  1. Zrealizowano działającą aplikację SPA spełniającą wymagania tematu 17.
  2. Wdrożono ważony ranking użyć (half-life 7 dni) oraz kontrolę użytkownika (pin, reset).
  3. Wprowadzono multi-user: każde konto ma własny panel i dane narzędzi.
  4. Badania wskazują przewagę modelu wagowego przy zmianie preferencji oraz dobrą jakość heurystyczną UI (śr. 3,4/4).
  5. Możliwe rozszerzenia: synchronizacja chmurowa, predykcja kontekstowa (pora dnia), badanie SUS na grupie studentów, A/B test M1 vs M2 in-vivo.
